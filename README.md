# vibe_mail

HTTP-API сервис для массовой рассылки писем. Клиент (админка `admin-front`)
создаёт кампании, добавляет получателей, запускает рассылку; отправка идёт
в фоне, а прогресс виден по статусам в БД.

Стек: **FastAPI** + **Uvicorn**, **SQLAlchemy 2.x** + **SQLite**, **Pydantic**,
менеджер зависимостей — **Pipenv**.

## Быстрый старт

```bash
pip install pipenv                                  # если ещё не стоит
PIPENV_VENV_IN_PROJECT=1 pipenv install             # создаёт .venv и ставит зависимости
cp .env.example .env                                # и заполнить SMTP
cp servers.example.yml servers.yml                  # и вписать доступы к панелям
make dev                                            # или: pipenv run python -m app
```

Проверить доступы до первого прогона, ничего не меняя на серверах:

```bash
make check_servers     # связь с панелями, авторизация, список клиентов
make check_smtp        # подключение и вход на почтовый сервер
```

После запуска:
- API доступно на `http://127.0.0.1:8000`
- интерактивная документация Swagger — `http://127.0.0.1:8000/docs`

Остановка: `Ctrl+C`.

Альтернативный запуск напрямую через интерпретатор виртуалки:

```bash
pipenv run python -m app --reload --port 8000
```

## Запуск в Docker

Один контейнер на всё: FastAPI отдаёт и API, и собранный фронт, поэтому адрес один и
CORS не нужен.

```bash
cp .env.example .env                # заполнить SMTP
cp servers.example.yml servers.yml  # заполнить доступы к панелям
mkdir -p data && cp vibe_mail.db data/   # если переносите существующую базу
make docker_build
make docker_up                      # интерфейс: http://localhost:8000
```

Логи — `make docker_logs`, остановка — `make docker_down`.

Что пробрасывается внутрь и почему:

| Что | Куда | Зачем |
|---|---|---|
| `servers.yml` | `/app/servers.yml` (ro) | доступы к панелям; в образ не попадают |
| `.env` | переменные окружения | SMTP; в образ не попадает |
| `./data` | `/data` | база кампаний и выданных конфигов переживает пересборку |
| `~/.ssh` | `/home/app/.ssh` (ro) | ключи, алиасы серверов из `config` и `known_hosts` |

Порт публикуется **только на 127.0.0.1**: у API нет аутентификации, а среди его ручек
есть отдача конфигов с приватными ключами. Наружу его выставлять нельзя.

Контейнер работает под uid 1000 — тем же, что и обычный пользователь на хосте: иначе
он не прочитает ключи (права 600) и не запишет в `./data`. Если ваш `id -u` отличается,
добавьте в `.env` строки `APP_UID=` и `APP_GID=` со своими значениями.

Пробники работают и внутри контейнера:

```bash
docker compose exec vibe-mail python check_servers.py
docker compose exec vibe-mail python check_smtp.py
```

## Конфигурация (`.env`)

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `SMTP_HOST` | хост SMTP-сервера | `smtp.gmail.com` |
| `SMTP_PORT` | порт (465 — SSL, 587 — STARTTLS) | `587` |
| `SMTP_USER` | логин отправителя | — |
| `SMTP_PASSWORD` | пароль приложения (не основной!) | — |
| `SMTP_USE_TLS` | STARTTLS для порта 587 | `true` |
| `SMTP_USE_SSL` | SSL для порта 465 | `false` |
| `DATABASE_URL` | путь к SQLite | `sqlite:///./vibe_mail.db` |

Для Gmail/Яндекса нужен **пароль приложения**, а не основной пароль аккаунта.

## API

Базовый префикс: `/api`.

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/health` | проверка здоровья |
| `POST` | `/api/campaigns` | создать кампанию |
| `GET` | `/api/campaigns` | список кампаний + прогресс |
| `GET` | `/api/campaigns/{id}` | кампания + счётчики |
| `POST` | `/api/campaigns/{id}/recipients` | добавить получателей (`{"items": [...]}`), атомарно |
| `GET` | `/api/campaigns/{id}/recipients` | список получателей |
| `POST` | `/api/campaigns/{id}/recipients/preview` | предпросмотр вставленного списка, ничего не пишет |
| `POST` | `/api/campaigns/{id}/recipients/import` | импорт вставленного списка |
| `POST` | `/api/campaigns/{id}/start` | запустить рассылку (202, воркер отправляет в фоне) |
| `POST` | `/api/campaigns/{id}/stop` | приостановить рассылку |
| `POST` | `/api/campaigns/{id}/retry-failed` | вернуть упавшие письма в очередь |
| `POST` | `/api/campaigns/{id}/configs/generate` | поставить конфиги в очередь на генерацию |
| `DELETE` | `/api/campaigns/{id}` | удалить кампанию |
| `POST` | `/api/recipients/{rid}/configs` | добавить получателю конфиги |
| `POST` | `/api/recipients/{rid}/configs/bind` | привязать сразу несколько клиентов панели |
| `DELETE` | `/api/recipients/{rid}` | удалить получателя |
| `GET` | `/api/configs/{cid}/download` | скачать файл конфига |
| `POST` | `/api/configs/{cid}/bind` | привязать конфиг к клиенту панели |
| `POST` | `/api/configs/{cid}/unbind` | снять привязку |
| `DELETE` | `/api/configs/{cid}` | удалить строку конфига |
| `GET` | `/api/servers` | список включённых серверов |
| `GET` | `/api/servers/{key}/clients` | клиенты панели этого сервера |

Пример создания кампании и запуска:

```bash
curl -X POST http://127.0.0.1:8000/api/campaigns \
  -H 'Content-Type: application/json' \
  -d '{"name":"Рассылка","subject":"Привет","body":"Текст письма"}'

curl -X POST http://127.0.0.1:8000/api/campaigns/1/recipients \
  -H 'Content-Type: application/json' \
  -d '{"items":[{"email":"a@b.c"},{"email":"x@y.z"}]}'

curl -X POST http://127.0.0.1:8000/api/campaigns/1/start
```

Импорт списка из таблицы. Колонки через таб: имя, почта, количество конфигов и
привязки к клиентам панелей — последние две необязательны.

```bash
curl -X POST http://127.0.0.1:8000/api/campaigns/1/recipients/import \
  -H 'Content-Type: application/json' \
  --data-binary $'{"text":"Plus_Vibe\tplusvibe@slop.com\t2\tru:existing1"}'
```

## Как это работает

- **Получатели и конфиги.** Список вставляется колонками из таблицы: имя, почта,
  количество конфигов и привязки — последние две необязательны. Строки с одинаковой
  почтой объединяются в одно письмо. Сначала `preview` показывает, что получится, потом
  `import` сохраняет: валидные строки создаются, проблемные возвращаются списком с
  номером строки.
- **Серверы и панели.** Конфиги берутся с VPN-панелей, описанных в `servers.yml`
  (см. `servers.example.yml`): AmneziaWG и wg-easy отдают файл `.conf`, 3x-ui — ссылку
  подписки. До панелей, слушающих localhost, приложение ходит `curl`'ом внутри
  SSH-сессии, до остальных — обычным HTTP.
- **Что уезжает получателю.** Файлы — вложениями, ссылки подписки — текстом в теле
  письма, следом памятка, чем всё это открыть. Клиент, заведённый на панели вручную,
  можно привязать к конфигу: программа заберёт его доступ, а не создаст второй.
- **Валидация до отправки.** Адреса проверяются при добавлении получателей
  (синтаксис, дубликаты в рамках кампании), а при `start` — готовность кампании.
  При любой проблеме — `400` со списком, старт не происходит.
- **Возобновление.** Статусы получателей (`pending`/`sent`/`failed`) хранятся в БД.
  При перезапуске процесса «зависшие» запущенные кампании подхватываются воркером
  автоматически.
- **Ретраи.** Временные ошибки (4xx, обрыв, таймаут) — до 3 попыток с паузой
  2/4/8 с и переподключением. Постоянные (5xx, отказ получателя/отправителя) —
  получатель помечается `failed`, рассылка продолжается.
- **Фоновая отправка.** Запрос `start` возвращает `202`; реальную отправку делает
  отдельный поток (`app/services/worker.py`), запущенный при старте приложения.
  Это не блокирует HTTP-запрос и позволяет фронту опрашивать прогресс.

## Заметки

- Легаси-CLI (`send_mail.py`, `import_csv.py`, `config.example.yaml`) удалён — вся
  логика живёт в `app/services/*`, глобальные настройки только через `.env`, а список
  VPN-серверов — в `servers.yml`.
- Миграций нет: таблицы создаются при старте (`Base.metadata.create_all`). Изменение
  схемы требует `make remake_db`, а он стирает данные — базу стоит скопировать заранее.
- У API нет аутентификации, поэтому он слушает только `127.0.0.1`. Выставлять его
  наружу нельзя: `/api/configs/{id}/download` отдаёт конфиги с приватными ключами.
