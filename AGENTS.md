# AGENTS.md — vibe_mail

Путеводитель для AI-агента по проекту **vibe_mail**: архитектура, инварианты и конвенции.

> Глобальные правила из `~/.claude/CLAUDE.md` про TypeScript/Vue/Composables **не
> относятся** к Python-части репозитория, но **применяются** к фронтенду в `admin-front/`.

## Что это
HTTP-API сервис массовой рассылки писем. Клиент (фронтенд `admin-front`) создаёт
кампании, добавляет получателей, запускает рассылку; отправка идёт в фоне, прогресс
виден по статусам в БД.

## Стек

Бэкенд:
- **FastAPI** + **Uvicorn** (`uvicorn[standard]`); Swagger на `/docs`.
- **SQLAlchemy 2.x** (sync, `Mapped[...]`) + **SQLite** (`vibe_mail.db`, gitignored).
- **pydantic-settings** — конфиг из `.env`; **pyyaml** — список VPN-серверов из
  `servers.yml`; **paramiko** — SSH к серверам; **httpx** — панели, доступные снаружи.
- **Pipenv** (`Pipfile` + `Pipfile.lock`), venv в `.venv/`.
- Линтер — **ruff** (конфиг в `pyproject.toml`): select E/W/F/I/UP/B/C4/SIM/RET/PTH/TC,
  ignore `E501` (длину держит форматтер) и `B008` (ложный позитив на `Depends()`).
- Язык комментариев и сообщений — **русский**.
- Тестов **нет** (пользователь явно отменил).

Фронтенд (`admin-front/`) — отдельный npm-проект, с Pipenv не связан:
- **Vite 8** + **Vue 3.5** (`<script setup>` + Composition API) + **TypeScript 5.x**.
- **shadcn-vue** поверх **Tailwind v4**, примитивы reka-ui, иконки `@lucide/vue`,
  тосты `vue-sonner`.
- Формы — `vee-validate` + `@vee-validate/zod` + `zod`. Роутер — vue-router 4.
- Стора нет (ни Pinia, ни Vuex): состояние живёт в композаблах и локальных `ref`.
- ESLint (flat config `admin-front/eslint.config.js`); в `ignores` — `dist/**`,
  `api-mocker/**`, `src/components/ui/**`, `src/apiService/types/vibe-mail.ts`.

## API (базовый префикс `/api`)
| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/health` | здоровье |
| `POST` | `/api/campaigns` | создать кампанию |
| `GET` | `/api/campaigns` | список + прогресс |
| `GET`  | `/api/campaigns/{id}` | кампания + счётчики |
| `POST` | `/api/campaigns/{id}/recipients` | добавить получателей (атомарно) |
| `GET` | `/api/campaigns/{id}/recipients` | список получателей |
| `POST` | `/api/campaigns/{id}/recipients/preview` | предпросмотр вставленного списка (dry-run) |
| `POST` | `/api/campaigns/{id}/recipients/import` | импорт вставленного списка (201, частичный) |
| `POST` | `/api/campaigns/{id}/configs/generate` | поставить недостающие конфиги в очередь (202); тело `{"servers": [...]}` ограничивает серверами, пустое — все |
| `GET` | `/api/servers` | список настроенных VPN-серверов (для кнопок генерации) |
| `GET` | `/api/servers/{key}/clients` | имена клиентов, живущих сейчас на панели (для привязки) |
| `POST` | `/api/configs/{id}/bind` | привязать конфиг к клиенту, заведённому на панели вручную |
| `POST` | `/api/configs/{id}/unbind` | снять привязку, вернуть производное имя |
| `GET` | `/api/configs/{config_id}/download` | скачать файл конфига (бинарный ответ, без конверта) |
| `POST` | `/api/campaigns/{id}/start` | запуск рассылки (202) |
| `POST` | `/api/campaigns/{id}/stop` | пауза (статус → NEW) |
| `DELETE` | `/api/campaigns/{id}` | удалить кампанию (200, MessageOutEnvelope) |
| `DELETE` | `/api/recipients/{rid}` | удалить получателя (204, без тела) |

## Ключевые инварианты (сохранять)
- **Конфигов у человека может быть несколько.** У получателя есть базовое имя
  (`Recipient.client_name`) и количество (`Recipient.config_count`); имена конфигов
  получаются нумерацией — `alice` и 3 дают `alice-1`, `alice-2`, `alice-3`. **Номер есть
  всегда, даже у единственного конфига**: иначе добавление второго потребовало бы
  переименовать первый, а в AmneziaWG переименования нет. Разделитель обязателен по той
  же причине читаемости: без него база с цифрой на конце (`alice2`) дала бы
  неоднозначное `alice21`. Имя собирается **только** в `models.config_client_name`
  (константа `CONFIG_NAME_SEPARATOR`); на фронте разделитель продублирован в
  `AddRecipientsDialog.vue` — подсказка рисуется до похода на бэкенд.
- **Имя конфига на панели глобально, поэтому базовые имена уникальны.** Два получателя
  с базой `alice` дали бы `alice-1` дважды, и второй упал бы на генерации с «клиент уже
  есть». Импорт ловит это раньше, проверяя оба источника: саму вставку (`_add_row`) и
  получателей, заведённых прошлыми импортами (`_reject_taken_names`). Конфликтная строка
  уезжает в `problems`, остальные импортируются.
- **Строка `Config` — это пересечение «номер конфига × сервер».** Серверов несколько
  (список в `servers.yml`, путь в `VPN_SERVERS_FILE`), и каждое имя заводится на каждом
  **включённом** сервере: три конфига и четыре сервера дают двенадцать строк.
  Уникальность держит `uq_config_recipient_seq_server`. Само имя в `Config` не хранится,
  а выводится из `Recipient.client_name` и `Config.seq` (свойство `Config.name`) — так
  переименование остаётся правкой в одном месте. `config_count` хранится явно, а не
  считается по `configs`: без включённых серверов конфигов нет, а количество знать надо.
  Ключ сервера (`Config.server_key`) — строка, а не внешний ключ: список серверов живёт
  в конфиге, а не в БД, поэтому **менять `key` после создания кампаний нельзя** — конфиги
  потеряют связь с сервером.
- **Два вида артефактов** (`ArtifactKind`): панели WireGuard (AmneziaWG, wg-easy) отдают
  **файл** — он уезжает вложением; 3x-ui отдаёт **ссылку подписки** — она уезжает текстом
  в теле письма. Что именно лежит в строке, говорит `Config.kind`; `Config.is_ready`
  проверяет нужное поле (`content` или `link`).
- **Панель ≠ транспорт.** Тип панели (`panel`) и способ доехать до неё (`transport`)
  задаются независимо у каждого сервера: `ssh` — панель слушает localhost, запрос идёт
  как `curl` внутри SSH-сессии; `direct` — панель смотрит наружу, ходим httpx. Адаптеры
  панелей про эту разницу не знают.
- **Версия 3x-ui определяется в рантайме** по разобранному конверту `{success, msg, obj}`,
  а не по коду ответа: на неизвестный путь панель отвечает и 404, и редиректом на форму
  входа (HTML со статусом 200), и последнее сошло бы за новый API. Пробуем новый
  `/panel/api/clients/list`, при
  404 откатываемся на старый `/panel/api/inbounds/*` с `settings`-JSON строкой.
  Авторизация выбирается отдельно и от версии не зависит: есть `auth.token` — Bearer,
  иначе `POST /login` с cookie-сессией. wg-easy поддержан только v15 (Basic Auth);
  при включённой 2FA его API не работает вовсе.
- **SSH — по ключу.** `services/ssh.py` разбирает `~/.ssh/config` через `paramiko.SSHConfig`
  (paramiko сам его не читает — ни алиасы, ни `IdentityFile`) и раскладывает по аргументам
  `connect()`. Заданное в `servers.yml` перекрывает найденное в `~/.ssh/config`; ключи и
  ssh-agent разрешены, пароль — запасной вариант. `ProxyJump` не поддержан.
- **Валидация ДО отправки**: синтаксис email (`EMAIL_RE` из `core/constants.py`) и
  дубликаты в кампании — при добавлении получателей; готовность кампании —
  `recipient_service.validate_campaign_ready` (есть получатели, есть хотя бы один
  включённый сервер и **у каждого получателя готов конфиг на каждом сервере**). При ошибке
  `start` возвращает `400` со списком, ничего не шлём: половинчатое письмо уже
  не переотправить.
- **Возобновление**: кампании со статусом `IN_PROGRESS` подхватываются воркером при
  старте процесса; получатели со статусом `PENDING` отправляются заново. Источник
  правды — статусы получателей в БД (`PENDING`/`SENT`/`FAILED`).
- **Статусы кампании** (`CampaignStatus`, `app/db/models.py`): `NEW` (при создании) →
  `start` переводит в `IN_PROGRESS`; `stop` возвращает в `NEW` — воркер перечитывает
  статус кампании перед каждым письмом, поэтому пауза срабатывает в пределах одного
  письма, а не после всей пачки; воркер по завершении всех получателей ставит `DONE`,
  а если хотя бы у одного статус `FAILED` —
  `DONE_WITH_ERRORS` («Завершена с ошибками»); `ERROR` — зарезервированный статус
  фатального сбоя кампании, сейчас нигде не выставляется. `DONE` и `DONE_WITH_ERRORS`
  терминальные — воркер подхватывает только `IN_PROGRESS`. В БД хранится имя enum
  (`NEW`/`IN_PROGRESS`/…), в API-ответе — значение (`new`/`in_progress`/…).
- **Импорт получателей**: вставка — от двух до четырёх колонок через таб
  (`имя_конфига<TAB>почта<TAB>количество<TAB>привязки`), как копируется диапазон из
  Google Sheets. Хвостовые колонки **необязательные**: без третьей — один конфиг, без
  четвёртой — привязок нет, поэтому старые двухколоночные вставки продолжают работать.
  Привязка записывается как `ru:adonm`, несколько — через запятую, и цепляется к первому
  конфигу (`import_service.BOUND_SEQ`): служебное имя у человека одно, остальные конфиги
  получают производные имена. **Ключ сервера обязателен**: короткие имена живут не на
  всех панелях, а угадывать, на каких, значило бы ходить на них прямо во время разбора
  и ронять импорт, когда сервер недоступен. Генерацию импорт не запускает — это делает
  кнопка на странице кампании. Разбор — только в
  `services/import_service.py`. Базовое имя у получателя одно, поэтому две строки с одной
  почтой и **разными** именами — противоречие: первая выигрывает, вторая уезжает
  в `problems`; повтор той же почты с тем же именем безвреден, количество берётся
  наибольшее. Импорт **частичный, не атомарный**: валидные строки сохраняются, проблемные
  возвращаются списком с номером строки и причиной (иначе одна строка без почты
  заблокировала бы весь список).
- **Количество — это «сколько должно стать», а не «сколько добавить».** Повторный импорт
  того же списка ничего не меняет; увеличенное число доводит получателя до него;
  **уменьшенное игнорируется** — удалять уже заведённых на панелях клиентов импорт
  не вправе. Дозаводится ровно недостающее, и одним механизмом
  (`import_service._missing_pairs`) закрываются оба случая: человеку добавили конфигов и
  в `servers.yml` добавили сервер. Базовое имя у существующего получателя не меняется —
  под ним уже заведены клиенты на панелях.
- **Генерация конфигов**: кнопки на странице кампании только **ставят в очередь** — меняют
  статус конфигов без артефакта (`PENDING`/`FAILED`) на `QUEUED` и отдают 202. Кнопок
  столько же, сколько включённых серверов, плюс «Сгенерировать все»: тело запроса
  `{"servers": [...]}` ограничивает постановку, пустой список — все серверы. Артефакты
  добывает отдельный фоновый поток `services/config_worker.py`: `QUEUED` → `GENERATING` →
  `READY` (или `FAILED` с текстом в `error`), коммит после каждого конфига. Адаптеры
  панелей он держит пулом по ключу сервера — одно соединение на сервер на весь прогон
  очереди. Панель, до которой не доехал сам запрос (`PanelUnreachable` — нет связи, не
  пустил SSH), помечается на весь проход очереди, и остальные её конфиги уходят в `FAILED`
  с той же причиной сразу: ждать таймаут отдельно на каждом из десятков конфигов — это
  десятки минут, а ответ будет тот же. При старте процесса зависшие `GENERATING`
  возвращаются в `QUEUED`. Готовые
  конфиги повторный запуск не трогает — догенерируются только недостающие. Файл лежит
  в БД (`configs.content`, BLOB), ссылка — в `configs.link`.
- **Клиента с занятым именем забираем, а не создаём заново** (`BasePanel.ensure_client`
  → `fetch_client`, иначе `_create_client`). На серверах живут клиенты, заведённые руками
  до появления программы; перевыпустить такого — оставить человека со старым конфигом на
  руках и лишним пиром на сервере. Плодить одноимённых панели всё равно не дают. Ошибка
  одного конфига не рушит очередь: она попадает в `configs.error` и видна в таблице
  бейджем с тултипом.
- **Имя для получателя и имя на панели — разные вещи.** `Config.name` всегда выводится
  из `Recipient.client_name` и номера: оно попадает в имя вложения и в подпись рядом со
  ссылкой, то есть его видит человек. `Config.panel_name` — то, чем клиент зовётся на
  самом сервере; совпадает с `name`, пока конфиг не привязан вручную. На панель ходят
  **только** с `panel_name` (`config_worker._process`, проверка занятости в
  `_reject_taken_external`), наружу отдают **только** `name`. Так короткие служебные
  имена (`adonm`, `treshcd`), под которыми клиенты заведены на `ru`, остаются на сервере
  и не уезжают получателю — расшифровать их он всё равно не сможет.
- **Имена, не ложащиеся на схему, привязываются вручную.** Автоматически совпадёт только
  то, что названо как `база-номер`; клиента с произвольным именем (`Ivanov`) сопоставить
  не по чему. Для этого у конфига есть `external_name`: `POST /api/configs/{id}/bind`
  ставит его и отправляет конфиг в очередь, воркер забирает артефакт тем же путём;
  массово то же самое делает четвёртая колонка импорта.
  На то, что видит получатель, привязка не влияет: `name` остаётся производным.
  Проверок две — имя должно существовать на панели, и один клиент панели не может быть
  привязан к двум конфигам **одной кампании**: тот же человек в новой рассылке — это тот
  же клиент на панели, и глобальный запрет закрыл бы повторную рассылку тем же людям. `unbind` возвращает производное имя и **сбрасывает артефакт**:
  он принадлежал чужому клиенту. Без привязки совпадения имён не случится, и на панели
  тихо появится дубль — это цена того, что сопоставлять не по чему.
- **Панели и их API**. **Имя конфига = имя клиента на сервере.**
  - **AmneziaWG Web UI** — `POST /api/servers/{id}/clients` одним вызовом создаёт клиента
    и возвращает текст конфига. Переименования клиентов в панели нет.
  - **wg-easy v15** — `POST /api/client` создаёт клиента и возвращает только его id,
    файл забирается вторым запросом `GET /api/client/{id}/configuration`. Поле с id
    сборки называют по-разному (`id`, `clientId`), а иные отвечают пустым телом, поэтому
    не нашли в ответе — ищем клиента по имени в списке (`WgEasyPanel._lookup_id`).
  - **3x-ui** — `POST /panel/api/clients/add` заводит клиента сразу в нужные `inbound_ids`,
    `GET /panel/api/clients/get/{email}` отдаёт его `subId`, а база ссылки подписки берётся
    из настроек панели (`subURI`, иначе `subDomain`/`subPort`/`subPath`) и кешируется на
    сессию — она одна на панель. Путь к настройкам от версии тоже зависит, поэтому
    пробуются оба (`XuiPanel.SETTINGS_PATHS`: `/panel/api/setting/all`, затем
    `/panel/setting/all`); если панель стоит за прокси и показывает свой внутренний
    адрес, базу задают в `servers.yml` полем `sub_base` и панель не спрашивают вовсе.
    **`subId` задаём равным имени конфига**,
    поэтому ссылка получается читаемой (`.../sub/alice-1`), а не со случайным хвостом;
    путь подписки при этом берётся из настроек панели и не трогается. Панель вправе
    почистить `subId`, поэтому он читается обратно, а расхождение логируется.
  - **`panel: fake`** — заглушка для разработки без доступа к серверам; что она изображает,
    задаётся полем `artifact`. Выданные клиенты хранятся в модуле, общие на ключ сервера
    и на весь процесс: у настоящей панели состояние живёт на сервере, и адаптеры из
    воркера и из HTTP-запроса обязаны видеть одно и то же.
- **Письмо**: файлы конфигов уезжают **вложениями**, ссылки подписки — текстом в конце
  тела, каждая с именем конфига и сервером (`MailSender._build_message`, `_links_block`):
  вложением ссылка быть не может, а без подписи человек не поймёт, какая ссылка для какого
  устройства. **Имя вложения обязательно содержит ключ сервера**
  (`Config.download_filename` → `alice-1_ru.conf`): один конфиг заводится на нескольких
  WireGuard-панелях под одним именем, и без ключа в письме оказались бы два вложения
  с одинаковым `alice-1.conf`. Воркер отдаёт
  отправителю ORM-конфиги получателя, контент берётся из БД; конфиг без артефакта
  пропускается при сборке, но до отправки дело не дойдёт — такую кампанию не даст
  запустить валидация.
- **Ретраи**: временные ошибки — до 3 попыток с паузой 2/4/8 с и переподключением
  (`mail_sender._is_temporary`); постоянные — `failed`, рассылка продолжается.
- **Фоновая отправка**: `start` отдаёт `202`, отправляет отдельный поток
  (`services/worker.py`), запущенный в `lifespan`. Запрос не блокируется.
- **Схема БД**: Alembic не подключён, таблицы создаются `Base.metadata.create_all` в
  `lifespan`. `create_all` **существующие таблицы не меняет**, поэтому миграции писать не
  нужно, а после правки моделей БД пересоздаётся (цель `remake_db` в `Makefile`).

## Модули — зоны ответственности
- `core/config.py` — `Settings` (pydantic-settings), `get_settings()` (кеш).
- `core/servers.py` — `ServerConfig`/`ServersConfig`: разбор `servers.yml`, типы панелей,
  транспортов и артефактов.
- `core/constants.py` — `EMAIL_RE`.
- `db/*` — ORM: `Campaign`, `Recipient`, `Config` (+ `ConfigStatus`) + сессия.
  `Config` — артефакт на паре «номер конфига — сервер»; базовое имя и количество
  лежат в `Recipient.client_name` / `config_count`, а `Config.external_name` перебивает
  производное имя для клиентов, привязанных вручную.
- `schemas/*` — pydantic-модели запрос/ответ (`from_attributes=True`).
- `services/mail_sender.py` — `MailSender`: connect/build/retry; в БД не ходит — получает
  готовые объекты кампании, получателя и его конфигов.
- `services/recipient_service.py` — валидация, добавление получателей, готовность.
- `services/campaign_service.py` — CRUD кампаний (создание/чтение/смена статуса/удаление), прогресс.
- `services/import_service.py` — разбор вставленного из таблицы списка (единственное место
  парсинга), предпросмотр и импорт получателей.
- `services/config_service.py` — постановка конфигов кампании в очередь, доступ к конфигу.
- `services/panels/` — адаптеры панелей (`AmneziaPanel`, `XuiPanel`, `WgEasyPanel`,
  `FakePanel`) и фабрика `build_panel(server)`. В БД не ходят, как `mail_sender`: получают
  имя клиента, возвращают `Artifact` — файл либо ссылку подписки.
- `services/transport.py` — как запрос доезжает до панели: `SshCurlTransport` (curl внутри
  SSH-сессии) и `DirectTransport` (httpx). Cookie держит транспорт, адаптеру всё равно.
- `services/ssh.py` — единственное место сборки аргументов `paramiko.connect()`, включая
  разбор `~/.ssh/config`.
- `services/server_service.py` — доступ к списку серверов из остального кода.
- `check_servers.py` (корень, `make check_servers`) — пробник панелей: поднимает то же
  соединение, что и генерация, читает список клиентов и базу подписки, ничего не меняя.
  Им проверяют доступы **до** первого боевого прогона — в воркере ошибка видна только
  статусом конфига. С `--bindings` (`make check_bindings`) сверяет `external_name` всех
  конфигов с живыми панелями и предлагает похожие имена: привязка с опечаткой иначе
  всплыла бы уже при генерации.
- `check_smtp.py` (корень, `make check_smtp`) — то же самое для почты: подключение,
  шифрование и вход тем же `MailSender._connect`, которым пользуется рассылка.
  С `--to адрес` отправляет одно тестовое письмо.
- `api/configs.py` — скачивание файла, привязка/отвязка и удаление строки конфига.
  Отвязка лишней строки её удаляет: строка сверх одной на сервер заводится только под
  конкретного клиента панели, и пустой она при следующей генерации завела бы лишнего.
- `api/recipients.py` — удаление получателя, добавление ему конфигов
  (`POST /{id}/configs`) и привязка сразу нескольких клиентов панели
  (`POST /{id}/configs/bind`, по конфигу на имя). Номера конфигов продолжаются
  отдельно по каждому серверу: у человека может быть пять доступов на одном и один
  на остальных, и сквозная нумерация плодила бы лишних клиентов.
- `composables/useTheme.ts` (фронт) — светлая и тёмная тема. Токены обеих лежат в
  `style.css` (`:root` и `.dark`), а свои статусные цвета компоненты объявляют через
  `:global(.dark) .класс`; композабл только держит класс `dark` на `<html>` и
  `color-scheme`, чтобы в тон пришли полосы прокрутки и поля ввода. Выбор хранится
  в localStorage; пока его нет — следуем системной теме. Инициализация вызывается
  в `main.ts` до `mount`, иначе страница моргает светлым.
- `services/worker.py` — фоновый поток отправки. Берёт только PENDING, поэтому
  перезапуск приложения посреди рассылки её продолжает, а не начинает заново. По той
  же причине упавшее письмо само не повторится — для этого есть
  `POST /api/campaigns/{id}/retry-failed`: возвращает FAILED в очередь и открывает
  кампанию для повторного запуска, не трогая тех, кому письмо уже ушло.
- `services/config_worker.py` — фоновый поток генерации конфигов.
- `api/*` — роутеры FastAPI; `deps.py` даёт `get_db` и `get_worker`.

## Архитектура бэкенда
- **Слоистая структура.** Путь запроса: `api/*` (роутеры) → `services/*` (бизнес-логика)
  → `db` (ORM). Роутеры тонкие: валидируют вход pydantic-схемами, вызывают сервисы,
  оборачивают результат. Сервисы не зависят от HTTP (`mail_sender` не знает про БД).
- **Единая обёртка ответов.** Все JSON-эндпоинты данных возвращают
  `ApiEnvelope[T]` = `{status: 'success'|'error', result, error}`. Для каждого ответа —
  явный подкласс в `schemas/envelope.py` (`CampaignReadEnvelope`, `ImportPreviewEnvelope`,
  `MessageOutEnvelope`, …) ради стабильных имён в OpenAPI (generic даёт хешированные
  суффиксы). Роутеры возвращают `ok(result)`. Ошибки (HTTPException,
  RequestValidationError, необработанные) перехватываются в `main.py` и тоже
  оборачиваются в `{status:'error', result:null, error}`.
- **Новый эндпоинт** трогает по порядку: `db/models.py` → `schemas/*` (+ свой подкласс
  конверта) → `services/*` → `api/*` → регенерация типов фронта.
- **Auth** — нет (локальное приложение). **CORS** — `CORSMiddleware` в `app/main.py`,
  список origin в `CORS_ORIGINS` (по умолчанию `http://localhost:5173`): в dev фронт
  ходит на бэкенд напрямую через `VITE_API_BASE_URL`, vite-прокси убран.

## Архитектура фронтенда
- **Слой API — `src/apiService/`** (фасад с адаптерами):
  - `httpClient.ts` — низкоуровневый `fetch`-обёртчик; базовый URL из `VITE_API_BASE_URL`
    (по умолчанию `/api`); бросает ошибку при `!response.ok` или `status === 'error'`.
  - `types/vibe-mail.ts` — **генерируется** из бэкендного `/openapi.json` через
    `openapi-typescript` (скрипт `generate:api`), руками не правится. Wire-типы берутся
    отсюда (`components['schemas']`).
  - `index.ts` — корневой баррель: `apiService.campaigns.*`, `apiService.recipients.*`,
    `apiService.servers.*`.
  - **На каждый домен своя папка**: `<domain>ApiTypes.ts` (доменные camelCase-типы +
    wire-типы), `apiService.ts` (методы домена), `adapters/`.
  - **Адаптеры**: для чтения — `campaignsListAdapter.ts`, `campaignsItemAdapter.ts`; для
    действий — verb-first (`createCampaignAdapter.ts`, `importRecipientsAdapter.ts`).
    Каждый дефолт-экспорт = `{ adaptParams, adaptResponseData }`: `adaptParams` маппит
    доменный вход → wire, `adaptResponseData` снимает обёртку `{status,result,error}` и
    переводит snake_case → camelCase.
  - **Поток вызова:** компонент/композабл → `apiService.<domain>.<method>(input)` →
    `adapter.adaptParams` → `httpClient` → `adapter.adaptResponseData`.
- **Композаблы** (`src/composables/`): базовый `useApiService` (`isLoading`/`data`/
  `execute`/`onDone`/`onError`, ошибки в консоль + тост) лежит в корне. Доменные — в
  `composables/data/`, по файлу на метод API, имя повторяет метод: `getCampaigns` →
  `useGetCampaigns` (возвращает `campaigns`/`getCampaigns`), действия verb-first:
  `importRecipients` → `useImportRecipients`. Каждый экспортирует свой `ERROR_MESSAGE`.
  Композаблы не вызывают lifecycle-хуки — `onMounted`/`onUnmounted` живут в страницах.

## Конвенции фронтенда
- **Стили наших компонентов — CSS Modules**, не Tailwind: `<style module>` и
  `:class="$style.foo"`. Tailwind остаётся только для сгенерированных
  `src/components/ui/**`, убирать его нельзя.
- **Имя корневого класса = имя компонента** в camelCase: `CampaignsTable.vue` →
  `.campaignsTable`, `CampaignDetailsPage.vue` → `.campaignDetailsPage`. Внутренние классы
  именуются по смыслу (`.headerRow`, `.infoCard`, `.statusNew`). Исключение —
  `SidebarMenu.vue`: его корень `<SidebarGroup>` без класса.
- **Токены темы — через CSS-переменные** (`var(--foreground)`, `var(--muted-foreground)`,
  `var(--destructive)`, `var(--border)`, `var(--radius-md)`); цвета статусных бейджей
  заданы литералами с тёмной веткой через `:global(.dark) .statusX`.
- **`!important` не используем**: стили SFC-модуля инжектятся после глобального Tailwind,
  поэтому при равной специфичности наш класс перебивает базовый вариант по порядку
  каскада, а тёмная ветка выигрывает по специфичности.
- **`src/components/ui/**` не правим руками** — CLI shadcn перезаписывает эти файлы.
  Компоненты добавляются через shadcn-vue CLI строго из каталога `admin-front`. Если
  сгенерированному компоненту нужен глобальный CSS (например `vue-sonner/style.css`), он
  импортируется в `src/style.css`, а не внутри `ui/**`.
- **UI-элементы — только из shadcn** (`@/components/ui/*`): свою вёрстку кнопок, инпутов
  и карточек из `div`/`button` не пишем.
- **Порядок блоков в `.vue`**: `<template>` → `<script setup lang="ts">` → `<style module>`.
- **`data-test`** — на всех интерактивных элементах и строках списков (по ним ищут в тестах).
- **Полинг** (`CampaignsPage.vue`, `CampaignDetailsPage.vue`): интервал 3 с, опрашиваем
  **только пока есть кампания в `in_progress`**; флаг `pollInFlight` защищает от
  наложения запросов; таймер снимается в `onUnmounted`; скелетоны показываются только при
  первой загрузке, фоновые тики обновляют данные тихо.
- **Комментарии**: не дублируем в комментариях то, что видно из имени файла и кода;
  комментируем только нетривиальную логику.

## Принятые решения и их причины
- **Конфиги вместо вложений.** Работа с файлами (модель `Attachment`, роутер вложений,
  импорт CSV, лимиты размера, легаси-CLI) вырезана из проекта целиком. Вместо неё —
  модель `Config` (`recipient_id` + `name`): пока это только имя конфига, которое уезжает
  в тело письма столбиком.
- **Файлы конфигов лежат в той же таблице** (`filename`, `content` BLOB, `size` в `configs`) —
  конфиги WireGuard весят единицы килобайт, отдельная сущность под файл не нужна.
- **Генерация вынесена в фоновый поток**, потому что реальный источник файлов — SSH к
  VPN-серверу: 30+ конфигов заблокировали бы HTTP-запрос. Очередь выражена статусом самого
  конфига, отдельного поля у кампании нет.
- **Формат вставки жёсткий** — ровно две колонки через таб. Именно так Google Sheets
  кладёт в буфер скопированный диапазон, а textarea принимает plain-text flavor. От
  альтернативных разделителей, третьей колонки, автоопределения порядка колонок и
  нечёткого матчинга отказались сознательно, чтобы не усложнять.
- **Парсинг только на бэке** — одно место (`services/import_service.py`). Он нормализует
  `\r\n` и невидимые символы (NBSP, zero-width, BOM) и **приводит почту к нижнему
  регистру** — в таком виде адрес и группируется, и сохраняется в БД, поэтому строки,
  отличающиеся только регистром, дают одного получателя и одно письмо.
- **Предпросмотр отделён от импорта**: `preview` — dry-run, ничего не пишет, и показывает
  только те конфиги, которых у получателя ещё нет (уже заведённые — отдельным полем
  `existing_configs`), чтобы цифры совпадали с тем, что реально добавится.
- **Первая колонка — имя конфига, а не человека**, поэтому при импорте `Recipient.name`
  остаётся `None` и в `To:` уходит голый адрес.

## Известные недоделки
- SSH-доступ только по паролю (`SSH_PASSWORD`); авторизации по ключу нет.
- Ограничения на суммарный размер вложений нет: конфиги весят сотни байт, но при переходе
  на реальные файлы стоит вернуть проверку лимита письма в `validate_campaign_ready`.
- Диалог импорта (`AddRecipientsDialog.vue`) закрывается кликом мимо окна и чистит
  textarea — вставленный текст теряется. Отложено осознанно.
- В `Pipfile` остался `pyyaml` от удалённого легаси-CLI: в `app/` он больше не используется.
- В рабочей копии лежит каталог `attachments/` с тестовыми файлами от удалённой фичи
  вложений.
